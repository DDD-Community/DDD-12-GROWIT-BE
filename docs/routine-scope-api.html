1. 반복 투두가 저장되는 방식

반복 투두는 하나의 레코드가 아니라 날짜별로 독립된 투두 여러 건으로 저장됩니다. 같은 반복에 속한 투두들은 서버 내부에서 동일한 루틴 식별자를 공유합니다.

3/2 (월)todo A
3/9 (월)todo B
3/16 (월)todo C
3/23 (월)todo D

"매주 월요일" 루틴을 만들면 종료일까지의 모든 날짜에 투두가 미리 생성됩니다. 따라서 범위 수정/삭제는 "이 루틴에 속한 투두 중 어디까지를 대상으로 할지" 고르는 동작입니다.

2. 범위 타입

값 대상 UI 문구
SINGLE 선택한 투두 1건 해당 투두만 수정 / 삭제
FROM_DATE 선택한 투두의 날짜를 포함해서 그 이후 전부 해당 날짜 이후 투두 수정 / 삭제
ALL 해당 루틴의 모든 투두 (과거 포함) 전체 반복 투두 수정 / 삭제
기준 날짜는 "선택한 투두의 원래 날짜"입니다 FROM_DATE의 경계는 URL 경로의 {id}가 가리키는 투두가 원래 갖고 있던 날짜입니다. 사용자가 폼에서 날짜를 바꿔 date로 다른 값을 보내더라도 경계는 바뀌지 않습니다. 수정과 삭제 모두 동일한 기준을 씁니다.

3. 수정 API

PUT/todos/{id}

Request Body

필드 타입 필수 설명
date string (YYYY-MM-DD) 필수 수정 후 투두 날짜
content string (1~30자) 필수 할 일 내용
goalId string | null 선택 연결할 목표 ID. 생략하면 목표 연결이 해제됩니다. 유지하려면 기존 값을 그대로 보내세요.
isImportant boolean 선택 생략 시 false로 저장됩니다.
routine object 조건부 필수 반복 설정. routineUpdateType이 FROM_DATE 또는 ALL이면 반드시 포함해야 합니다. 없으면 400.
routineUpdateType SINGLE | FROM_DATE | ALL 조건부 필수 적용 범위. 반복 투두에 routine을 함께 보낼 때는 반드시 지정해야 하며, 생략하면 400입니다. routine 없이 내용·날짜만 고칠 때는 생략해도 되고, 그때는 해당 투두 1건만 바뀌고 반복 연결은 유지됩니다.

routine 객체

필드 타입 설명
repeatType DAILY | WEEKLY | BIWEEKLY | MONTHLY 반복 주기. routine 을 보낼 때 필수 — 누락하거나 모르는 값이면 400입니다.
duration.startDate string (YYYY-MM-DD) 반복 시작일
duration.endDate string (YYYY-MM-DD) 반복 종료일. 시작일보다 앞설 수 없습니다.
repeatDays string[] (MONDAY …) 주간/격주 반복에서 요일 지정. 일간·월간에서는 무시됩니다. 보내지 않으면 기존 요일 설정이 사라집니다.

예시 — 해당 날짜 이후 전부 수정

PUT /todos/todo-b
Content-Type: application/json

{
  "goalId": "goal-1",
  "date": "2026-03-09",
  "content": "러닝 40분",
  "isImportant": false,
  "routine": {
    "repeatType": "WEEKLY",
    "duration": { "startDate": "2026-03-02", "endDate": "2026-03-23" }
  },
  "routineUpdateType": "FROM_DATE"
}

Response

200 OK — 본문 없음입니다. 수정 후 목록을 다시 조회해 화면을 갱신하세요.

FROM_DATE / ALL은 투두 ID가 바뀝니다 서버가 대상 투두를 지우고 새로 만들기 때문에, 요청에 사용한 {id}는 응답 후 더 이상 존재하지 않습니다. 같은 요청을 재시도하면 404가 납니다. 수정 후에는 반드시 목록을 다시 조회하세요. SINGLE은 ID가 유지됩니다.
완료 상태는 같은 날짜가 다시 생성될 때 이어집니다 재생성 후에도 존재하는 날짜의 완료 표시는 보존됩니다. 다만 요일이나 주기를 바꿔 날짜가 어긋나면 (예: 월요일 반복 → 화요일 반복) 옛 날짜는 사라지므로 그 완료 이력도 함께 사라집니다.

에러

상태 상황
400 routineUpdateType이 FROM_DATE/ALL인데 routine이 없거나 기간이 유효하지 않음
400 반복 투두에 routine을 보내면서 routineUpdateType을 지정하지 않음
400 FROM_DATE인데 duration.endDate가 선택한 투두의 날짜보다 앞섬 (삭제만 되고 대체 회차가 생기지 않는 조합)
400 repeatType이 없거나 알 수 없는 값
400 이미 연결된 목표의 같은 날짜에 투두가 10개 (기존에 목표가 연결된 투두에만 적용되며, FROM_DATE/ALL 로 생성되는 나머지 날짜는 검사하지 않습니다)
404 투두가 없거나 본인 소유가 아님

4. 삭제 API

DELETE/todos/{id}?routineDeleteType={SINGLE|FROM_DATE|ALL}

파라미터 위치 필수 설명
id path 필수 선택한 투두 ID
routineDeleteType query 선택 반복 투두면 지정하세요. 생략하면 해당 투두 1건만 삭제됩니다. 
DELETE /todos/todo-b?routineDeleteType=FROM_DATE

200 OK — { "data": "삭제가 완료되었습니다." }

5. 조회 응답의 routine 필드

수정 요청에 넣을 routine은 조회 응답에서 그대로 가져다 쓰면 됩니다. 

GET /todos?date=2026-03-09

{
  "data": [
    {
      "todo": {
        "id": "todo-b",
        "goalId": "goal-1",
        "date": "2026-03-09",
        "content": "러닝 30분",
        "isCompleted": false,
        "isImportant": false,
        "routine": {
          "repeatType": "WEEKLY",
          "duration": { "startDate": "2026-03-02", "endDate": "2026-03-23" },
          "repeatDays": ["MONDAY"]
        }
      },
      "goal": { "id": "goal-1", "name": "건강 챙기기" }
    }
  ]
}

routine이 null이면 반복 투두가 아니므로 범위 선택 UI를 띄우지 않습니다.

6. 시나리오별 결과

기준 상황: 매주 월요일 루틴 — 3/2, 3/9, 3/16, 3/23. 사용자가 3/9 투두를 열었습니다.

SINGLE — 해당 투두만

3/2그대로
3/9변경
3/16그대로
3/23그대로

반복 연결은 유지되고 투두 ID도 그대로입니다.

FROM_DATE — 해당 날짜 이후

3/2그대로
3/9변경 (포함)
3/16변경
3/23변경

선택한 3/9이 포함됩니다. 3/9 이후 투두는 새 ID로 다시 만들어집니다.

ALL — 전체 반복

3/2변경
3/9변경
3/16변경
3/23변경

과거분까지 전부 대상입니다. 재생성 범위는 요청에 실은 duration을 따르므로, 시작일을 오늘로 바꿔 보내면 과거 투두는 사라집니다.

FROM_DATE 삭제

3/2남음
3/9삭제
3/16삭제
3/23삭제

7. 자주 하는 실수

routine을 빼고 FROM_DATE/ALL을 보내기 서버는 대상 투두를 지우고 다시 만드는 방식이라, routine이 없으면 "무엇을 다시 만들지"를 알 수 없습니다. 이 조합은 400으로 거절되니 조회 응답의 routine을 그대로 실어 보내세요.
조회 응답의 duration을 임의로 넓혀 보내기 FROM_DATE로 시리즈를 나누면 뒤쪽 시리즈는 새 반복이 되고 서버는 좁혀진 기간(기준일 ~ 종료일)을 돌려줍니다. 이 값을 무시하고 원래의 넓은 시작일을 다시 보내면, 그 시리즈에서 ALL을 눌렀을 때 앞쪽 시리즈가 이미 차지한 날짜에까지 투두를 만들어 같은 날 투두가 중복됩니다. 항상 마지막 조회 응답의 duration을 그대로 쓰세요.
goalId를 생략하기 부분 수정(PATCH)이 아니라 전체 교체(PUT)입니다. goalId를 빼면 null로 덮어써져 목표 연결이 끊기고 목표 달성률 집계에서도 빠집니다. isImportant도 같은 방식으로 false가 됩니다.
repeatDays를 빼고 되돌려 보내기 월·수·금 반복이던 투두를 수정하면서 repeatDays를 생략하면 요일 지정이 사라져 주 1회로 축소됩니다. 조회 응답의 값을 그대로 유지해 보내세요.
수정 후 이전 ID를 재사용하기 FROM_DATE/ALL 이후에는 목록을 다시 조회해야 합니다. 응답 본문이 없으므로 낙관적 업데이트(optimistic update)로 화면만 바꿔두면 실제 데이터와 어긋납니다.

문의는 백엔드 채널로. 이 문서는 ToDoController, RoutineServiceImpl의 실제 동작을 기준으로 작성되었습니다.
