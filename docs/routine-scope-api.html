반복 투두 범위 API

반복(루틴) 투두를 해당 투두만 / 해당 날짜 이후 / 전체 범위로 수정하거나 삭제하는 인터페이스 명세입니다.

Base URL /todos 인증 필요 (Bearer) Content-Type application/json
세 줄 요약
  • 반복 투두는 하나의 레코드가 아니라 날짜별로 나뉜 여러 건입니다. 범위 선택은 "그 중 어디까지를 대상으로 할지"를 고르는 동작입니다.
  • routine을 요청에 담을 때는 routineUpdateType을 반드시 함께 보내야 합니다. 빠지면 400입니다.
  • FROM_DATE의 경계는 요청 본문의 date가 아니라 수정 대상 투두가 원래 갖고 있던 날짜입니다.

1. 반복 투두가 저장되는 방식

반복 투두는 날짜별로 독립된 투두 여러 건으로 저장됩니다. 같은 반복에 속한 투두들은 서버 내부에서 동일한 루틴 식별자를 공유하고, 조회 응답에서는 각 투두가 같은 routine 객체를 갖는 것으로 보입니다.

3/2 (월)todo A
3/9 (월)todo B
3/16 (월)todo C
3/23 (월)todo D

"매주 월요일" 루틴을 만들면 종료일까지의 모든 날짜에 투두가 미리 생성됩니다. 즉 투두 하나를 수정한다는 것은 이 목록 중 일부를 갈아끼운다는 뜻입니다.

범위가 FROM_DATE 또는 ALL이면 투두가 새로 만들어집니다 서버는 대상 투두들을 지우고 새 회차를 다시 생성합니다. 따라서 그 범위에 포함된 투두들의 id는 요청 전후로 달라집니다. 화면에 들고 있던 id는 버리고 목록을 다시 조회하세요. (완료 여부는 날짜 기준으로 이어받으므로 유지됩니다.)

2. 공통 규약

인증

모든 엔드포인트는 로그인 사용자 토큰이 필요합니다.

Authorization: Bearer <accessToken>

성공 응답

엔드포인트 상태 코드 바디
PUT /todos/{id} 200 없음 (빈 응답)
DELETE /todos/{id} 200 { "data": "삭제가 완료되었습니다." }
GET /todos/{id} 200 { "data": { ...투두 } }

수정 응답에는 바디가 없습니다. 수정 결과(특히 갈라진 루틴의 새 기간)를 화면에 반영하려면 수정 후 목록/상세를 다시 조회해야 합니다.

에러 응답

HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "message": "반복 설정(routine)을 보낼 때는 적용 범위(routineUpdateType)를 함께 지정해야 합니다."
}

404는 대상 투두가 없거나 다른 사용자 소유일 때, 500은 서버 내부 오류일 때 반환됩니다.

3. 범위 타입

값 대상 UI 문구 예시 기존 투두 id
SINGLE 선택한 투두 1건 해당 투두만 수정 / 삭제 유지
FROM_DATE 선택한 투두의 날짜를 포함해서 그 이후 전부 해당 날짜 이후 투두 수정 / 삭제 수정 시 바뀜
ALL 해당 루틴의 모든 투두 (과거 포함) 전체 반복 투두 수정 / 삭제 수정 시 바뀜
기준 날짜는 "선택한 투두의 원래 날짜"입니다 FROM_DATE의 경계는 URL 경로의 {id}가 가리키는 투두가 원래 갖고 있던 날짜입니다. 사용자가 폼에서 날짜를 바꿔 date에 다른 값을 보내더라도 경계는 바뀌지 않습니다. 수정과 삭제 모두 같은 기준을 씁니다.

4. 수정

PUT/todos/{id}

Request Body

필드 타입 필수 설명
date string yyyy-MM-dd 필수 수정 후 투두 날짜
content string (1~30자) 필수 할 일 내용
goalId string 선택 연결할 목표 id. 생략하면 기존 연결이 해제됩니다(전체 교체 방식) — 값을 유지하려면 항상 함께 보내세요.
isImportant boolean 선택 중요 표시 운영(main) 계열
time string HH:mm 선택 투두 시각 develop 계열
category enum 선택 NOW / STEADY / SKIP / DELETE develop 계열
routine object 조건부 반복 설정. 아래 routine 객체 참고. 보낼 경우 routineUpdateType이 반드시 함께 있어야 합니다.
routineUpdateType enum 조건부 SINGLE / FROM_DATE / ALL

운영(main) 계열과 develop 계열은 배포 브랜치에 따라 필드 구성이 다릅니다. 운영 서버는 isImportant를, develop 서버는 time과 category를 받습니다. 나머지 필드와 반복 동작은 양쪽이 동일합니다.

routine 객체

필드 타입 필수 설명
duration.startDate string yyyy-MM-dd 필수 반복 시작일
duration.endDate string yyyy-MM-dd 필수 반복 종료일. 시작일보다 앞설 수 없습니다.
repeatType enum 필수 DAILY(매일) / WEEKLY(매주) / BIWEEKLY(격주) / MONTHLY(매월)
repeatDays string[] 선택 MONDAY … SUNDAY. WEEKLY/BIWEEKLY에서 여러 요일을 지정할 때만 사용합니다. 비우면 기준 투두와 같은 요일로 반복합니다.

범위별 동작

routineUpdateType 내용·날짜 변경 반복 설정(routine) 변경 완료 이력
SINGLE 선택한 1건만 반영되지 않습니다. 반복 주기·기간을 바꾸려면 FROM_DATE 또는 ALL을 쓰세요. 그대로 유지
FROM_DATE 기준일 포함 이후 전부 반영 — 기준일부터 새 루틴으로 갈라집니다 같은 날짜의 완료 표시는 이어받습니다
ALL 해당 루틴 전체 (과거 포함) 반영 — 보낸 기간·주기로 전부 다시 생성 같은 날짜의 완료 표시는 이어받습니다
반복이 없던 투두를 반복으로 바꿀 때 routine과 함께 routineUpdateType을 보내야 합니다. ALL을 권장합니다. 이 경우 기존에 없던 회차가 종료일까지 새로 생성됩니다.

요청 예시

① 해당 투두만 수정 (반복은 그대로)

PUT /todos/todo-0308
{
  "goalId": "goal-1",
  "date": "2026-03-09",
  "content": "아침 러닝 5km",
  "routineUpdateType": "SINGLE"
}

내용만 바꿀 때는 routine을 아예 보내지 않아도 됩니다. 이때 반복 연결은 유지됩니다.

② 해당 날짜 이후 전부 수정

PUT /todos/todo-0309
{
  "goalId": "goal-1",
  "date": "2026-03-09",
  "content": "아침 러닝 10km",
  "routine": {
    "duration": { "startDate": "2026-03-02", "endDate": "2026-04-27" },
    "repeatType": "WEEKLY"
  },
  "routineUpdateType": "FROM_DATE"
}

todo-0309가 원래 3/9 투두라면 3/9 이후만 바뀌고, 3/2는 옛 내용으로 남습니다. duration.startDate로 무엇을 보내든 경계는 3/9입니다.

③ 전체 반복 수정

PUT /todos/todo-0309
{
  "goalId": "goal-1",
  "date": "2026-03-09",
  "content": "아침 러닝 10km",
  "routine": {
    "duration": { "startDate": "2026-03-02", "endDate": "2026-04-27" },
    "repeatType": "WEEKLY",
    "repeatDays": ["MONDAY", "THURSDAY"]
  },
  "routineUpdateType": "ALL"
}

400이 되는 조건

조건 message
routine을 보냈는데 routineUpdateType이 없음 반복 설정(routine)을 보낼 때는 적용 범위(routineUpdateType)를 함께 지정해야 합니다.
routineUpdateType이 FROM_DATE/ALL인데 routine이 없거나 불완전 반복 범위를 수정하려면 반복 설정(routine)이 필요합니다.
FROM_DATE인데 duration.endDate가 기준일보다 앞섬 반복 종료일은 수정 기준일보다 앞설 수 없습니다.
repeatType이 비어 있음 반복 주기(repeatType)는 필수입니다.
repeatType이 정의되지 않은 값 알 수 없는 반복 주기입니다: {보낸 값}
같은 목표·같은 날짜에 투두가 이미 10개 해당 날짜에 이미 TODO 가 10개 입니다.
date 누락, content가 1~30자 범위 밖 필드별 검증 메시지

5. 삭제

DELETE/todos/{id}?routineDeleteType={SINGLE|FROM_DATE|ALL}

파라미터 위치 필수 설명
id path 필수 삭제 대상 투두 id
routineDeleteType query 선택 생략하거나 반복이 아닌 투두면 해당 투두 1건만 삭제합니다. 반복 투두는 범위를 지정할 수 있습니다. 
DELETE /todos/todo-0309?routineDeleteType=FROM_DATE

200 OK
{ "data": "삭제가 완료되었습니다." }

삭제는 데이터를 물리적으로 지우지 않고 삭제 표시만 남깁니다(soft delete). 삭제된 투두는 모든 조회에서 제외되므로 클라이언트가 신경 쓸 차이는 없습니다.

6. 조회 응답의 routine 필드 다루기

조회 응답의 투두에는 자신이 속한 반복 정보가 함께 들어 있습니다.

GET /todos/todo-0316

{
  "data": {
    "id": "todo-0316",
    "goalId": "goal-1",
    "date": "2026-03-16",
    "content": "아침 러닝 10km",
    "isImportant": false,
    "isCompleted": false,
    "routine": {
      "duration": { "startDate": "2026-03-09", "endDate": "2026-04-27" },
      "repeatType": "WEEKLY",
      "repeatDays": null
    }
  }
}

develop 계열에서는 isImportant 대신 time과 category가 내려옵니다. routine 구조는 양쪽이 같습니다.

수정 폼을 열 때는 반드시 최신 조회 응답의 routine을 쓰세요 FROM_DATE로 수정하면 뒤쪽 구간이 새 반복으로 갈라지고, 그 반복의 duration.startDate는 기준일로 좁혀집니다. 화면에 캐시해 둔 옛 duration(더 이른 시작일)을 그대로 되돌려보내면, 그 시리즈에서 ALL을 눌렀을 때 앞쪽 시리즈가 차지한 날짜까지 다시 만들어져 같은 날 투두가 2건이 됩니다.

7. 시나리오별 결과

기준 상황: 매주 월요일 반복 — 3/2, 3/9, 3/16, 3/23. 사용자가 3/9 투두를 열어 내용을 바꿉니다.

SINGLE

3/2그대로
3/9변경
3/16그대로
3/23그대로

FROM_DATE

3/2그대로
3/9변경
3/16변경
3/23변경

3/9 이후는 새 반복으로 갈라지고, 3/2는 옛 반복에 남습니다.

ALL

3/2변경
3/9변경
3/16변경
3/23변경

FROM_DATE로 날짜(요일)까지 옮긴 경우

3/9(월) 투두를 열어 날짜를 3/11(수)로 바꾸고 "이후 전체 수정"을 누르면:

3/2 (월)그대로
3/9 (월)삭제
3/11 (수)신규
3/16 (월)삭제
3/18 (수)신규
3/23 (월)삭제
3/25 (수)신규

경계는 옮긴 날짜(3/11)가 아니라 원래 날짜(3/9)입니다. 3/9부터 잘라내고, 새 요일로 회차를 다시 만듭니다.

8. 자주 하는 실수

① routine만 보내고 범위를 생략 예전에는 서버가 ALL로 해석해 반복 전체를 다시 만들었고, 그 과정에서 과거 완료 이력이 사라졌습니다. 지금은 400으로 거절합니다. 반복 설정을 건드리는 요청에는 항상 범위를 함께 보내세요.
② 범위만 보내고 routine을 생략 FROM_DATE/ALL은 "지우고 다시 만드는" 동작이라 반복 설정이 없으면 대량 삭제가 됩니다. 지금은 400으로 거절합니다.
③ SINGLE로 반복 주기를 바꾸려는 시도 SINGLE은 그 투두의 내용·날짜만 바꿉니다. 함께 보낸 routine은 조용히 무시되므로, 사용자가 바꾼 반복 설정이 저장되지 않은 것처럼 보입니다. 반복 설정 변경 UI에서는 FROM_DATE 또는 ALL만 노출하세요.
④ 수정 후 화면의 id 재사용 FROM_DATE/ALL 수정은 대상 투두를 새로 만듭니다. 수정 직후에는 목록을 다시 조회하고, 가지고 있던 id로 후속 요청을 보내지 마세요(404).
⑤ 종료일을 기준일보다 앞으로 당기기 "이후 전체 수정"을 누르면서 종료일을 기준일 이전으로 바꾸면 지울 대상만 있고 만들 회차가 없어 데이터가 사라집니다. 서버가 400으로 막지만, 날짜 선택 UI에서 미리 제한하는 편이 좋습니다.

9. FE 적용 체크리스트

  • 반복 투두 수정 폼에서 "해당 날짜 이후" 버튼을 노출하고 routineUpdateType: "FROM_DATE"를 전송합니다.
  • routine을 담는 모든 요청에 routineUpdateType을 함께 넣습니다. (누락 시 400)
  • 반복이 없던 투두에 반복을 새로 거는 화면에서도 routineUpdateType: "ALL"을 보냅니다.
  • 반복 설정 변경 UI에서는 SINGLE을 선택지에서 제외하거나, 선택 시 반복 설정 입력을 비활성화합니다.
  • 수정 성공(200) 후에는 목록을 다시 조회해 id와 routine.duration을 갱신합니다.
  • goalId를 유지하려면 수정 요청에 항상 포함시킵니다. (생략 시 연결 해제)
  • 400 응답의 message를 그대로 노출하거나, 위 조건표에 맞춰 안내 문구를 매핑합니다.
