반복 투두 범위 API

반복 투두를 해당 투두만 / 해당 날짜 이후 / 전체 범위로 수정하거나 삭제하는 API 사용법입니다.

경로 prefix /todos 인증 필요 (Bearer) Content-Type application/json
세 줄 요약
  • 반복 투두는 한 건이 아니라 날짜별로 쪼개진 여러 건입니다. 범위 선택은 그중 어디까지 손댈지 고르는 일입니다. 이 문서는 하루치 한 건을 회차, 회차들의 묶음을 반복이라고 부릅니다.
  • routine을 보낼 때는 routineUpdateType을 반드시 함께 보내세요. 빠지면 400입니다 — 이번 배포부터 생긴 규칙이라 기존 코드가 깨질 수 있습니다. (0절에서 확인하세요.)
  • FROM_DATE·ALL 수정에서 반복 설정을 그대로 두고 내용만 고치면 회차를 다시 만들지 않아 id와 완료 이력이 유지됩니다. 반복 주기·요일·기간이나 날짜를 하나라도 바꾸면 대상 회차를 지우고 새로 만들어 id가 바뀝니다. 응답 바디가 없으니 어느 쪽이든 성공 후 목록을 다시 조회하세요.

0. 기존 코드에서 확인할 곳

PUT /todos/{id} 요청에 routine을 담는 코드를 전부 찾으세요. 이번 배포부터 그 요청에 routineUpdateType이 없으면 400입니다.

기존 코드 유형별 조치
지금 코드 조치
routine을 보내지 않음 (내용·날짜만 수정) 영향 없음. 고칠 것 없습니다.
routine을 보내면서 routineUpdateType이 없음 깨집니다. 예전 서버는 이 요청을 ALL로 처리했으므로, 동작을 그대로 유지하려면 "routineUpdateType": "ALL"을 추가하세요.
routineUpdateType이 FROM_DATE/ALL인데 routine을 안 보냄 깨집니다. routine을 함께 보내세요 (만드는 법).
DELETE 호출 바뀐 것 없습니다.

1. 반복 투두가 저장되는 방식

반복 투두는 날짜별로 독립된 회차 여러 건으로 저장됩니다. 조회하면 같은 반복에 속한 회차마다 같은 routine 값이 담겨 옵니다. (서버 내부에서는 이 묶음을 "루틴"이라고 부르지만, API에서 다룰 일은 없습니다.)

3/2 (월)회차 A
3/9 (월)회차 B
3/16 (월)회차 C
3/23 (월)회차 D

"매주 월요일" 반복을 만들면 종료일까지의 모든 날짜에 회차가 미리 생성됩니다. 즉 투두 하나를 수정한다는 것은 이 목록 중 일부를 갈아끼운다는 뜻입니다.

FROM_DATE·ALL 수정은 일정을 바꿀 때만 회차를 새로 만듭니다 repeatType, repeatDays, duration.startDate, duration.endDate, 그리고 date가 조회했을 때와 모두 같으면 서버는 회차를 지우지 않고 내용만 바꿉니다. id와 완료 이력이 그대로 유지됩니다.

다섯 값 중 하나라도 다르면 대상 회차를 지우고 다시 생성하므로 그 범위의 id가 전부 달라집니다. 화면에 들고 있던 id는 버리고 목록을 다시 조회하세요. (옛 id로 요청하면 404입니다.) 이때 완료 여부는 같은 날짜가 다시 만들어질 때만 이어받습니다.

예외 — 반복이 없던 투두에 반복을 새로 거는 경우에는 그 투두를 지우지 않고 그대로 쓰므로 id가 유지됩니다.

4. 수정

PUT/todos/{id}

PUT은 부분 수정이 아니라 전체 교체입니다 보내지 않은 필드는 대부분 초기화됩니다. 수정 폼은 조회 응답의 모든 필드를 담아 보내야 합니다. 필드별 동작은 아래 표의 "생략하면" 열을 확인하세요.

Request Body

FROM_DATE·ALL 요청의 routine 만드는 법

사용자가 반복 설정을 건드리지 않았더라도 FROM_DATE·ALL에는 routine이 반드시 들어가야 합니다(없으면 400). 다음 순서로 만드세요.

  1. 수정 폼을 열기 직전에 조회한 응답의 routine을 그대로 복사합니다. 목록 캐시에 오래 들고 있던 값은 쓰지 마세요.
  2. 사용자가 실제로 바꾼 항목만 덮어씁니다.
  3. duration.startDate는 조회값 그대로 두고 손대지 않습니다.

startDate가 범위별로 다르게 쓰이기 때문입니다.

범위별 duration.startDate의 역할
범위 duration.startDate의 역할
FROM_DATE 회차를 만들 때는 쓰이지 않고 서버가 기준일로 좁혀 저장합니다. 다만 조회값과 다르게 보내면 일정이 바뀐 것으로 보고 회차를 전부 지웠다 다시 만듭니다 (id가 바뀌고 완료 이력이 어긋납니다). 조회값을 그대로 보내세요
ALL 그대로 반복 시작일이 됩니다. 조회값과 다른 값을 넣으면 다른 반복이 차지한 날짜까지 침범해 같은 날 투두가 2건이 됩니다

범위별 동작

범위별 수정 동작 비교
routineUpdateType 내용·날짜 변경 반복 설정(routine) 변경 완료 이력
SINGLE 선택한 1건만 반영되지 않습니다. 함께 보낸 routine은 서버가 그냥 버립니다 그대로 유지
FROM_DATE 기준일 포함 이후 전부 반영 — 기준일부터 새 반복으로 갈라집니다 일정이 그대로면 그대로 유지. 일정을 바꾸면 같은 날짜의 완료 표시만 이어받습니다
ALL 해당 반복 전체 (과거 포함) 반영 — 보낸 기간·주기로 전부 다시 생성 일정이 그대로면 그대로 유지. 일정을 바꾸면 같은 날짜의 완료 표시만 이어받습니다
날짜·요일을 옮기면 완료 이력이 사라집니다 반복 주기·요일·기간·날짜를 그대로 두고 내용만 고치면 회차를 다시 만들지 않으므로 투두 ID 와 완료 이력이 모두 그대로 유지됩니다. 아래는 일정 자체를 바꿀 때의 이야기입니다. 완료 여부는 같은 날짜일 때만 이어받습니다. 월요일 반복을 수요일로 옮기면 새 회차의 날짜가 전부 달라지므로, 사용자가 쌓아온 완료 기록이 전부 초기화됩니다. 요일이나 날짜를 바꾸는 수정에서는 확인 모달에 이 사실을 알려주세요.
반복이 없던 투두를 반복으로 바꿀 때 routine과 함께 routineUpdateType을 보내야 합니다. ALL을 보내세요. 이 경로는 범위 값을 보지 않기 때문에 SINGLE을 보내도 똑같이 전 회차가 생성됩니다 — 의도가 드러나도록 ALL로 통일하는 편이 안전합니다.

이때 회차는 duration.startDate가 아니라 그 투두의 date부터 만들어집니다. 두 값을 같게 보내세요. 그 투두의 date가 duration 범위 밖이면 400으로 거절됩니다.

요청 예시

① 이 회차만 수정 (반복은 그대로)

PUT /todos/todo-0309
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "goalId": "goal-1",
  "date": "2026-03-09",
  "content": "아침 러닝 5km",
  "routineUpdateType": "SINGLE"
}

내용만 바꿀 때는 routine을 아예 보내지 않아도 됩니다. 이때 반복 연결은 유지됩니다.

② 해당 날짜 이후 전부 수정

PUT /todos/todo-0309
{
  "goalId": "goal-1",
  "date": "2026-03-09",
  "content": "아침 러닝 10km",
  "routine": {
    "duration": { "startDate": "2026-03-02", "endDate": "2026-04-27" },
    "repeatType": "WEEKLY"
  },
  "routineUpdateType": "FROM_DATE"
}

todo-0309가 원래 3/9 회차라면 3/9 이후만 바뀌고, 3/2는 옛 내용으로 남습니다. 여기서 startDate에 3/2를 넣은 것은 조회 응답을 그대로 실어 보냈기 때문이고, FROM_DATE에서는 이 값이 무시되므로 안전합니다. 같은 값을 ALL에 넣으면 결과가 완전히 달라집니다 — ③과 6절을 보세요.

③ 전체 반복 수정

PUT /todos/todo-0309
{
  "goalId": "goal-1",
  "date": "2026-03-09",
  "content": "아침 러닝 10km",
  "routine": {
    "duration": { "startDate": "2026-03-02", "endDate": "2026-04-27" },
    "repeatType": "WEEKLY",
    "repeatDays": ["MONDAY", "THURSDAY"]
  },
  "routineUpdateType": "ALL"
}

ALL에서는 startDate가 그대로 쓰입니다. 반드시 직전 조회 응답의 값이어야 합니다.

수정 요청이 400으로 거절되는 조건과 응답 메시지
조건 message
routine을 보냈는데 routineUpdateType이 없음 반복 설정(routine)을 보낼 때는 적용 범위(routineUpdateType)를 함께 지정해야 합니다.
routineUpdateType이 FROM_DATE/ALL인데 routine이 없거나, duration이 없거나, endDate가 startDate보다 앞섬 반복 범위를 수정하려면 반복 설정(routine)이 필요합니다.
FROM_DATE인데 duration.endDate가 기준일보다 앞섬 반복 종료일은 수정 기준일보다 앞설 수 없습니다.
보낸 반복 설정으로 만들 수 있는 회차가 하나도 없음 (예: 월·수·금 반복을 일요일만으로 바꾸면서 종료일을 이틀 뒤로 당김) 이 반복 설정으로는 만들 수 있는 회차가 없습니다. 반복 주기와 기간을 확인해 주세요.
반복이 없던 투두에 반복을 걸 때, 그 투두의 date가 duration 범위 밖 투두 날짜가 반복 기간 밖입니다.
repeatType이 비어 있음 반복 주기(repeatType)는 필수입니다.
repeatType이 정의되지 않은 값 알 수 없는 반복 주기입니다: {보낸 값}
같은 목표·같은 날짜에 회차가 이미 10개 해당 날짜에 이미 TODO 가 10개 입니다.
date 누락, content가 1~30자 범위 밖 필드별 검증 메시지 — 아래 주의 참고
content 검증 메시지를 그대로 노출하지 마세요 실제 제약은 1~30자인데 서버가 돌려주는 문구는 "할 일은 5자 이상 30자 이하여야 합니다."입니다(서버 수정 예정). 이 항목만은 자체 문구로 매핑하세요. 나머지 메시지는 위 표대로 노출해도 됩니다.

하루 10개 제한은 요청 본문의 date 하루에 대해서만 검사합니다. FROM_DATE·ALL로 여러 날짜에 회차를 만들 때 나머지 날짜는 검사하지 않으므로, 반복 수정으로 특정 날짜가 10개를 넘길 수 있습니다.

6. 조회와 재조회

조회 응답의 회차에는 자신이 속한 반복 정보가 함께 들어 있습니다. 아래는 일정을 바꾸는 수정(예: 요일 변경)으로 시리즈가 갈라진 뒤의 응답입니다 — duration.startDate가 기준일로 좁혀져 내려옵니다. 내용만 고치는 수정에서는 갈라짐이 없어 값이 그대로입니다. 

GET /todos/todo-0316

{
  "data": {
    "id": "todo-0316",
    "goalId": "goal-1",
    "date": "2026-03-16",
    "content": "아침 러닝 10km",
    "isImportant": false,
    "isCompleted": false,
    "routine": {
      "duration": { "startDate": "2026-03-09", "endDate": "2026-04-27" },
      "repeatType": "WEEKLY",
      "repeatDays": null
    }
  }
}

앞의 예시 ②를 실행한 뒤 3/16 회차를 조회하면 이렇게 보입니다. duration.startDate가 요청에 보낸 3/2가 아니라 기준일인 3/9로 좁혀져 내려온 것을 확인하세요 — 다음 수정 요청에는 이 값을 써야 합니다. (time·category 계열 서버에서는 isImportant 대신 time과 category가 내려옵니다.)

수정 폼을 열 때는 반드시 최신 조회 응답의 routine을 쓰세요 FROM_DATE로 수정하면 뒤쪽 구간이 새 반복으로 갈라지고, 그 반복의 duration.startDate는 기준일로 좁혀집니다. 화면에 캐시해 둔 옛 duration(더 이른 시작일)을 그대로 되돌려보내면, 그 반복에서 ALL을 눌렀을 때 앞쪽 구간이 차지한 날짜까지 다시 만들어져 같은 날 투두가 2건이 됩니다.

갈라진 앞쪽 구간은 서버가 함께 좁혀줍니다. 위 예시에서 3/2 회차의 duration은 기준일 직전인 3/8까지로 줄어 내려옵니다. 그러니 앞쪽에서 ALL을 눌러도 뒤쪽 구간의 날짜를 침범하지 않습니다 — 단, 이 역시 조회한 값을 그대로 되돌려보낼 때만 성립합니다.

수정·삭제 후 재조회

  • SINGLE은 id가 그대로라 낙관적 업데이트를 해도 됩니다.
  • FROM_DATE·ALL은 응답에 결과가 없고, 일정을 바꾼 경우에는 id까지 바뀌므로 낙관적 업데이트를 하지 마세요. 로딩 상태를 띄우고 재조회 결과로 그리는 편이 안전합니다.
  • FROM_DATE·ALL은 기준일부터 반복 종료일까지 전부 새로 만듭니다. 지금 보고 있는 주간뿐 아니라 캐시에 들고 있는 모든 주간을 무효화하세요.
  • 실패했다고 무조건 재시도하지 마세요. 서버가 처리한 뒤 응답만 유실된 경우, 같은 요청을 다시 보내면 대상 id가 이미 사라져 404가 돌아옵니다. 재시도 전에 목록을 조회해 실제 반영 여부를 확인하세요.

8. 자주 하는 실수

🔴 빨강은 서버가 막지 못하고 데이터가 어긋나는 경우, 🟠 주황은 서버가 400으로 거절해 사용자에게 에러만 보이는 경우입니다.

🔴 ① 오래된 duration을 그대로 되돌려보내기 서버가 막지 못합니다. 6절의 경고를 참고해, 수정 폼을 열기 직전에 조회한 값을 쓰세요.
🔴 ② 수정 후 화면의 id 재사용 FROM_DATE·ALL 수정은 회차를 새로 만듭니다. 수정 직후에는 목록을 다시 조회하고, 가지고 있던 id로 후속 요청을 보내지 마세요(404).
🟠 ③ routine만 보내고 범위를 생략 예전에는 서버가 ALL로 해석해 반복 전체를 다시 만들었고, 그러면서 지난 완료 기록까지 함께 날아갔습니다. 지금은 400으로 거절합니다.
🟠 ④ 범위만 보내고 routine을 생략 FROM_DATE·ALL은 "지우고 다시 만드는" 동작이라 반복 설정이 없으면 지우기만 하고 다시 만들지 못합니다. 지금은 400으로 거절합니다.
🟠 ⑤ 종료일을 기준일보다 앞으로 당기기 "이후 전체 수정"에서 종료일을 기준일 이전으로 보내면 지울 대상만 있고 새로 만들 회차가 없습니다. 서버가 400으로 거절하므로 데이터는 안전하지만, 사용자는 원인을 알기 어려운 에러를 봅니다. 날짜 선택 UI에서 기준일 이전을 아예 못 고르게 막으세요.
🟠 ⑥ SINGLE로 반복 주기를 바꾸려는 시도 SINGLE은 그 회차의 내용·날짜만 바꿉니다. 함께 보낸 routine은 서버가 그냥 버리는데 200이 돌아오기 때문에, 사용자 눈에는 저장된 것처럼 보이고 다시 열어야 안 바뀐 걸 압니다. 반복 설정 변경 UI에서는 FROM_DATE·ALL만 노출하세요. (단 반복이 없던 투두에 반복을 새로 거는 경우는 예외로, SINGLE을 보내도 전 회차가 생성됩니다.)

9. FE 적용 체크리스트

  • 반복 투두 수정 폼에 "해당 날짜 이후" 버튼을 노출하고 routineUpdateType: "FROM_DATE"를 전송합니다.
  • routine ↔ routineUpdateType은 양방향 필수입니다. routine을 보내면 범위를, FROM_DATE·ALL을 보내면 routine(duration + repeatType)을 반드시 함께 넣습니다.
  • 반복이 없던 투두에 반복을 새로 거는 화면에서도 routineUpdateType: "ALL"을 보내고, duration.startDate를 그 투두의 date와 같게 맞춥니다.
  • 반복 설정 변경 UI에서는 SINGLE을 선택지에서 제외하거나, 선택 시 반복 설정 입력을 비활성화합니다.
  • 수정·삭제 성공 후에는 목록을 다시 조회해 id와 routine.duration을 갱신합니다. FROM_DATE·ALL은 캐시된 모든 주간을 무효화합니다.
  • goalId는 항상 포함시킵니다. isImportant(또는 time)도 조회값을 그대로 실어 보냅니다 — 빠뜨리면 초기화됩니다.
  • 날짜·요일을 옮기는 수정에서는 완료 기록이 초기화된다는 안내를 확인 모달에 넣습니다.
  • 삭제 버튼에도 범위 선택을 붙이고, ALL 선택 시 "지난 기록도 사라지며 되돌릴 수 없습니다"를 확인 모달에 노출합니다.
  • 400 응답의 message를 노출하되, content 길이 메시지만은 자체 문구로 대체합니다. 메시지 문자열로 분기하지 마세요 — 서버 문구가 바뀌면 조용히 깨집니다.
  • routineUpdateType·date 값은 전송 전에 형식을 검증합니다. 잘못된 값은 400이 아니라 500으로 돌아옵니다.
